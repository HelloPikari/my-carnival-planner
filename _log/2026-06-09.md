## Design decisions from grill-me (Phase 4.5 spec)

### What we're building
A context-aware MCP server that guides users through trip planning without hallucinating or losing context between sessions. Decisions logged in roadmap under Phase 4.5.

### Trip context model
- Hard required (real DB columns on `trips`): `arrival_date`, `departure_date`, `party_size`, `budget_usd`
- Soft/optional: JSONB `metadata` on trips (vibe preference, experience level, etc.)
- Remaining budget is computed: `budget_usd - SUM(confirmed itinerary item costs)`

### Tool enforcement model
- **Server-enforced:** only `arrival_date`/`departure_date` gate tool responses (return `{status: "missing_context"}` if absent)
- **LLM-enforced:** `party_size`, `budget_usd`, soft prefs — gathered conversationally via tool descriptions, not server-gated
- **Server skewing:** `party_size` skews band recommendations; remaining `budget_usd` skews accommodation/fete ranking

### New MCP tools needed
`get_carnival_seasons`, `create_trip`, `get_my_context`, `update_trip_context` — plus enhancements to all existing read tools

### LLM creates trips directly
No web form required for MVP. LLM runs intake → calls `create_trip` → immediately in planning mode. Web form is an alternative entry point.

### Active trip resolution
Server auto-selects most upcoming incomplete trip for the authenticated user. Ambiguous (multiple upcoming trips) → returns response asking which to plan for.

### Data decisions
- Budget is a raw USD number; tiers/ranges are a display concern, not a storage concern — LLM reasons about fit
- Carnival Monday is computed from year (calendar math), not stored — standard Easter algorithm
- Accommodation pricing: don't store price ranges — LLM handles display reasoning
- Accommodation data gaps: amenities, safety/walkability/location ratings, minimum stay — all present in Airtable extract, just weren't being seeded

# Session 3 — 2026-06-09 (late)

## What happened

Steve tested PR #10 in production via Claude Desktop as both admin and non-admin. Three reactive fixes landed; one design principle codified.

## Bugs caught in production testing

1. **Past seasons leaked through `get_carnival_seasons`** (PR #11). Original filter used `status != 'archived'`, but the seeded 2026 season was `status: 'active'` and never got updated when it ended. End users could see 2026 as a plannable season in June 2026.
   - Fix: both `get_carnival_seasons` and `resolveActiveTrip` now filter on `endDate IS NULL OR endDate >= CURRENT_DATE`. Calendar-based, not status-based.
   - Tests switched to a test-scoped future season (year 2098/2099) so they're stable as time advances.

2. **Empty array → LLM hallucination** (PR #12). After fix #1, `get_carnival_seasons` correctly returned `[]` (no future seasons seeded). Claude Desktop fell back to its training data and invented carnival info rather than telling the user the system had no data.
   - Fix: wrap empty case in steering envelope with `status`, `seasons: []`, `message`, and `guidance` fields. The `guidance` includes explicit don'ts ("do NOT invent dates", "do NOT fall back to general knowledge").
   - **Codified as a project standard** in `_specs/mcp-design-principles.md` — "closed-loop steering" is principle #1. Future agents see a pointer to it in `CLAUDE.md`. Phase 4.6 ("Steering Pass") added to roadmap to apply the pattern across remaining tools.

3. **Internal terminology leaking to end users** (PR #13). The PR #12 message included "seeded" — dev jargon. End user would see this if the LLM surfaced the message verbatim.
   - Fix: rewrite the user-facing copy as plain English; move internal context ("filtered out by endDate", "not loaded into the database yet") to `guidance` where it belongs.
   - Updated principles doc to make the audience separation explicit: `message` is end-user-facing UI copy with banned-vocabulary rules; `guidance` is LLM-only and uses precise internal terms freely.
